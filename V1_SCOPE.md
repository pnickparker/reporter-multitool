### The 35-minute test, and the processing limit rebuilt from measurements (2026-10-12, night)

**The decisive test worked.** A 35:24 interview (Drive holds 3.61 GB — iOS's "preparing" step re-encoded it up from the 1.66 GB the Files app showed, which is also why it took 6 minutes to start; the upload itself took ~18 min over Wi-Fi) was held by the old formula ("too long"), then **Transcribe now** processed it on Vercel in **159 s**: transcript ready at +116 s (5,749 words, 232 turns, a clean A/B split — the 2-speaker default working on a real interview), 9 best moments at +132 s (top score 92), ready with 9 post drafts at +159 s — about 53% of the 5-minute allowance.
**Where the time goes (timed separately):** the transcription service took only **42 s for the 35 minutes (~50x real time)**; moving the file Drive → service took ~74 s on Vercel (~49 MB/s; 156 s from the dev Mac at 23 MB/s); the AI steps ~43 s. **So the file's size, not the recording's length, mostly decides the time** — the old formula had this backwards (5.5 MiB/s moving, 0.06 s per audio second), which is why it wrongly rejected this video, and why Nick's Adobe-style "~30 minute" cap would have been unnecessarily strict.
**New formula** (`src/lib/assets/processing-limits.ts`): 55 s fixed + size ÷ 40 MB/s + 0.03 s per audio second, limit still 260 s; if the length is unknown it's guessed from the size (conservatively). Each figure is padded 20–60% beyond what was measured. Checked against every real data point: the 35-min/3.61 GB, 5:20/613 MB and 557 MB recordings are allowed; the 7.6 GB recording is held. **Rule of thumb it implies:** about 40 minutes of 1080p video, about 25 minutes of 4K phone video (these hit the size ceiling, roughly 5–6 GB), and audio up to about 1.5 hours; beyond that it's saved with the amber note and **Transcribe now** still tries. Only one large data point exists, so the padding is deliberate; a long-audio test (an hour or more) would tighten it. The message now reads "too long or large". **Tester guidance should say size, not just minutes.**
**Side findings:** sizes over ~2.1 GB are stored as unknown (null) until the column is widened (by design); an old video in iCloud makes the phone's "preparing" step slow, and the Files route was no faster (6 min to start).

### Audio-only recording — revisited (2026-10-12, night) — decision: don't build an in-app recorder yet

### Real-phone force-quit test, round 1 on the new build (2026-10-12): eight retries, then "(error network)" — twice

Nick, on the new build (it showed the new "Connection dropped — retrying (4 of 8)…" line), uploading `IMG_0954.mov` (533.8 MB, Wi-Fi, other sites loading fine): **Try again** twice, and both times it cycled through all 8 retries and ended on "Upload to Drive failed partway through (error network)", with the waiting card and backup intact (so nothing was lost). **What that tells us:** the retry counter resets whenever any piece succeeds, so eight failures in a row means *the same piece* failed every time — something specific to that piece, not a generally flaky connection — and "network" meant the browser never got an HTTP answer at all (the server never answered with an error code). **What we couldn't tell:** my code reported every such failure as "network", including the phone failing to *read* the recording out of its own storage, a timeout, or a real connection error. **Changes made (tested only against fake failures, not yet on a phone):** (1) the failure message now says why — "couldn't read the recording (NotReadableError)", "timed out", or the browser's own error such as "TypeError: Load failed" — and the same reason shows on the retry line; (2) after any failed piece the next try uses a smaller piece (4 MB → 2 → 1 → … → 256 KB) and grows back after four successes, so a connection or phone that can't push 4 MB through in one request can still get across in smaller bites. ### Force-quit resume froze at 52% (2026-10-12) — silent requests had no deadline

Nick's first force-quit test (the most important one): started an upload, swiped Safari away at about half, reopened, tapped **Resume upload** — the card came back (the phone-side copy survived the force-quit, as designed), but the upload then sat at 52% for minutes with no error. **Cause (hole confirmed in code; exact trigger not confirmed):** a request that goes silent never errors by itself, and the retry logic only runs when a request *ends*, so a request that never ends froze the upload forever. A likely trigger: the piece in flight when Safari was killed may still be running on the server against Drive's upload session, so Drive stalls the resume's first request. **Fix:** every piece now has a 120 s deadline in the browser (30 s for the "what do you have?" query) and a 100 s deadline on the server's request to Drive (answers 504 promptly), after which the existing retry-and-resume path takes over, and the screen says "Connection dropped — retrying (n of 8)…" instead of looking frozen. Verified with a fake server that goes silent on one piece (it times out, asks Drive, resumes, finishes). Needs a real-phone re-test of the force-quit flow on the new build.

**Follow-up, same day: Resume kept stalling after 1–2% each time, on Wi-Fi that was otherwise fine.** Each Resume made a little progress (52% → 54% → 55%) and froze again. A local reproduction against real Drive (start a piece, kill it mid-send like swiping Safari away, then resume, three rounds) did **not** stall — Drive finished the interrupted piece itself and every resume ran at normal speed — so the "leftover request blocks the upload" theory is ruled out. What *does* differ after a force-quit is where the file comes from: before, the phone's own file; after, a copy read back out of the browser's own storage (IndexedDB), and Safari is known to be unreliable streaming a large stored file straight into a network request. **Working theory, not confirmed on a phone:** that. **Change:** each 4 MB piece is now read into memory first (`arrayBuffer()`, inside the same deadline) and sent as a plain buffer, instead of handing the browser a slice of the file to stream. Verified: fake-server tests (clean upload, silent request, failure then resume) and a real-browser run (fail at 27%, reload, Resume read the rest back out of storage and finished in 11 s). ### Goal: long-form recordings (set by Nick, 2026-10-11) — not built, nothing here is decided

**The goal:** handle podcast-length recordings — 40 minutes and well beyond — end to end (upload, transcript, quotes, post drafts). Nick is a podcast host and producer who records long-form interviews, and would use this himself; he is also the first user who isn't just a field reporter. Today's design deliberately caps processing (`src/lib/assets/processing-limits.ts`, estimate must stay under 260s because Vercel Pro functions max out at 300s), so a 40-minute video uploads safely but is marked "too long to process automatically" with the original kept in Drive.

**Evidence so far (real iPhone, 2026-10-11):** a 40+ minute video uploaded over Wi-Fi with the weaker cell signal and was still going at 31% after about 10 minutes — so the upload alone is on the order of half an hour. Through it, airplane mode twice (error shown, **Try again** resumed from where it stopped), leaving Safari for another app and returning, and switching Safari tabs all resumed correctly, and the progress box confirmed a phone-side backup copy was kept for a file that large. **Result of that 40+ minute test (4,731.7 MB, `.mov`): the upload reached Drive in full, then the final "save it" step failed — a real bug, found only because of this test.** The database column for file size (`Asset.fileSizeBytes`) is a 32-bit integer (max ~2.1 GB); Drive reported 4,961,594,257 bytes, so the save errored with "value out of range for type integer" and the app showed "Upload finished but couldn't be saved." Reproduced in a rolled-back transaction, nothing changed. Recovery: Drive had the complete file, so Claude ran the corrected save step on the stuck row (project "Quick Capture — Oct 12, 2026"); it is now linked to its Drive file and shows as saved-but-not-transcribed. **Fix in the code:** sizes over 2.1 GB are stored as unknown (null) via `storableFileSize()` in `src/lib/assets/create-asset.ts` (nothing reads the stored size; the processing estimate uses Drive's real number). **Proper fix still to do — after the design branch is merged, not before:** widen the column to 64-bit (`BigInt`); doing that now would risk the live site, whose older code expects a 32-bit number, and BigInt also needs handling wherever an asset is returned as JSON. Anything past ~2.1 GB is normal for long-form video, so this is on the path to the goal. Also confirmed in the field: the backup copy held a ~5 GB file in the phone's storage, and the **Try again** card was showing correctly. Two lessons: (1) test with real extremes — this bug only appears above 2.1 GB; (2) the phone-side copy is stored per web address, and Nick's tab was on a per-build preview address, so that copy can't be resumed from the next build's address — another reason testers should only use one stable address. **Share video on that 4.7 GB file failed with "Couldn't fetch file" after a couple of minutes (Nick, real iPhone).** Cause: the server route behind Share (`/api/assets/[id]/file`) said it streamed, but actually downloaded the entire file into server memory before sending it, which works for small clips and cannot work for large ones — a ~600 MB interview would likely have failed too. **Fixed on the branch:** the route now streams piece by piece (like the playback route), has the longer time allowance, stops pulling from Drive if the browser gives up, and sends the size first. The Share button reads that size before downloading anything and, above 500 MB, immediately says "Too big to share from here (4.6 GB)" with an **Open in Drive** link instead of working for minutes. The 500 MB limit is a cautious guess, not a measured one — the phone must hold the whole file in memory to open the share sheet, and the real failure point on iPhone/Android is unknown, so **next test: Share video on ~300 MB, ~700 MB and ~1 GB files and raise or lower `MAX_SHAREABLE_BYTES` (`src/components/share-file-button.tsx`) from the results.** Verified locally: the 4.7 GB item reports too-big in 3.5 s, a 7 MB video still prepares in 2.5 s and the share sheet receives the real file. Real fix for huge originals later: a wrapped native app or a streaming download. Also seen on that item after the amber change: it now reads "Saved, not transcribed".

**Design rule behind it (Nick, 2026-10-11): capture must never be refused or lost; processing can wait.** *"I can't tell you how many times I thought I was doing a 5 minute interview but wound up spending an hour with someone. You just don't know."* Even if a long recording is saved and the transcript has to be run later, that's acceptable (not ideal) — what's never acceptable is leaving an interview and finding the app didn't have what you needed. What already honors this: the length check runs *after* the upload, so nothing is ever blocked from being recorded or saved. Gaps: (a) an over-limit recording currently ends in the red **Error** state with no way to "transcribe it later" — it should show as neutral/amber "Saved — transcript not made yet" instead, and (b) a **Transcribe now/later** action needs the webhook-based transcription below, since it can't run inside one function either.

**What reaching the goal would take (ideas, in rough order of leverage — verify before building):**
1. **Transcription that doesn't depend on a single function run.** The background work currently runs inside one function bounded by `maxDuration`. AssemblyAI can call a webhook when a transcript is done, so the app could start the job, return immediately, and finish when called back (already on the deferred list as "async/webhook transcription"). This, not the upload, is what actually removes the length ceiling.
2. **Faster uploads.** Drive can't be written to directly from a browser (CORS), so every 4 MB piece is relayed through our server one at a time — likely the bottleneck. Storage the browser can write to directly (with signed upload URLs, in parallel pieces) would be faster. This becomes a new trigger for the "leave Google Drive?" question (see "Storage and native-app thinking" below).
3. **Audio-only for long recordings.** A 40-minute interview is hundreds of MB as audio but gigabytes as video. If the transcript is the point, recording or extracting audio first would shrink uploads dramatically (extraction in the browser is heavy; recording audio-only is easy).
4. **Per-tier limits.** The single processing-limit constant was designed to become per-plan; long-form is the natural paid tier (see BUSINESS_NOTES.md on credits).
5. **Getting huge originals back out.** **Share video** loads the whole file into phone memory, which will not scale to multi-gigabyte files; needs a streaming download or a wrapped native app.
6. **Cost check.** Transcription is billed per audio hour and the AI steps per amount of text, so cost per interview scales with length — part of the cost-per-interview research already on the list. A very long transcript may also need splitting for the quote-flagging step.

### Upload resilience (2026-10-10) — a phone video failed mid-upload

Nick's iPhone video upload (on the preview branch) died with "Upload to Drive failed partway through." Cause not confirmed: Drive had plenty of room (88 GB of 2 TB), the chunk size is valid, and the request had started (an orphaned `UPLOADING` row remains), so one chunk got a non-OK response from Drive or our relay and the old code gave up on the first error. Fix: each chunk now retries up to 4 times with backoff; before retrying, the client asks Drive how many bytes it actually has (new "status query" on `/api/uploads/chunk`, which passes Drive's `Range` back as `X-Drive-Range`) and resumes from there, so a lost reply can't corrupt or restart the file. Now a failed upload keeps its file on screen with a **Try again** button, and "Try again" *resumes*: the same Drive session is asked what it already has and only the rest is sent (if the bytes had all arrived and only the final save failed, nothing is re-sent). Patience was also raised to 8 retries with a capped backoff (about 75 seconds of signal loss or sleep tolerated before giving up). If Drive has forgotten the session (404/410) it starts a fresh upload with the same file; a network error during the check just reports and lets the user tap again. ### Storage and native-app thinking (2026-10-09) — decisions about *when*, nothing built

Prompted by Nick asking, while approving an in-app player, whether it's time to leave Google Drive and whether to build native iOS/Android apps (the app that inspired him, Rode Capture, is iOS-only).

**Drive: not yet.** The player streams files Drive → our server → the phone, which is fine for a handful of testers. The triggers that should reopen the question: (1) the first paying outside newsroom — real per-customer accounts force a choice between each customer's own Drive and storage we run (see BUSINESS_NOTES.md); (2) playback complaints (Drive is not a media server and the extra hop adds delay); (3) Drive API quota or terms problems at higher use. Consistent with the earlier open question in this file ("is Drive more infrastructure than v1 needs") and the BLOX exit thinking (an acquirer re-platforms storage anyway).

**Native apps: stay web-first.** Why Rode Capture is iOS-only: it's an accessory for Rode's hardware microphones and needs deep camera/audio control a web page can't get, one platform is far cheaper than two native codebases and two store reviews, and its audience skews iPhone. This app's job (upload, transcribe, review, share) doesn't need that, and testers are on both iOS and Android. Real limits of the web approach, worth watching for in tester feedback: a web app can't be a target in the iPhone share sheet ("send this video from Photos into the app"); an upload can stall if the phone locks or the browser is backgrounded mid-way; background recording and push notifications are limited on iOS. Cheap steps before any native work: make it an installable home-screen app (PWA). If the limits above become the real pain, wrap the same web app in a native shell (e.g. Capacitor) for both stores rather than rewriting. Decide on evidence from testers, not in advance. **Actual fix: chunked upload relayed through our own server.** Same init/finalize shape as before, but the file's bytes now go browser → our server → Drive in pieces, instead of browser → Drive directly:
- `POST /api/quick-capture/init` or `POST /api/projects/[id]/assets/init` — unchanged: small JSON request (filename + MIME type) creates the `Asset` row and a Drive resumable-upload session server-to-server (no CORS issue there — this call was never made by the browser). `AssetType` (AUDIO vs VIDEO) is inferred from the MIME type. `createResumableUploadSession()` lives in `src/lib/storage/google-drive.ts` (a raw REST call — the `googleapis` client library doesn't expose "just give me the session URL").

Validates the upload URL actually targets `googleapis.com/upload/drive` before relaying, so this can't become an open proxy to arbitrary URLs.
- `POST /api/assets/[id]/finalize` — unchanged: records the resulting Drive file ID and kicks off transcription via `after()`.

## What v1 is

A **web app** that proves one end-to-end loop:

**Upload/record a clip → transcribe it → surface quotable moments → generate social post drafts → export.**

Not the mobile app. Not the full brief. One thin, working slice, built to be extended rather than thrown away.

## Users

- Nick, plus 2 freelance reporter testers. Flat permissions — everyone's a peer, no roles/admin tiers yet.
- Basic accounts/login from day one (retrofitting auth later is painful even for 3 users).

## Capture

- **Upload only** for v1 — no in-browser recording yet. Reporters record with their phone's native camera/voice memo app, then upload the file.
- Both **audio and video** files supported from day one (near-equal cost to build; the AI pipeline treats them the same — audio track out, everything downstream is identical).
- Expected content shape for testing: **short clips, 3-10 minutes** (player/coach interviews, not hour-long podcast episodes). This shapes several decisions below — revisit if usage shifts toward long-form (e.g. Fredcasts) later.
- Growth path (not v1): in-browser mic/camera recording via the browser's MediaRecorder API, which may get us close to "never leave the app" without needing a native mobile app at all. Native app stays a later option if browser recording proves insufficient for run-and-gun field use.

## Storage

- **Google Drive**, via the Drive API — not a dedicated object-storage service (S3/R2).
- Why: Nick already pays for Google storage (no incremental cost), and sharing a Drive folder with freelance testers is a workflow they already know.
- Pattern: Nick's Google account connects to the app once (OAuth). The app writes into a folder in his Drive. Testers get edit access to that folder the normal way (Drive sharing) — they don't need their own OAuth grant to the app for storage purposes.
- Known limitation, accepted for now: Drive doesn't support efficient range-request video seeking the way dedicated storage + a CDN does. This matters for hour-long content; it's a non-issue at 3-10 minute clip lengths, where a browser can just progressively download the whole file.
- **Storage is written as an abstraction in code**, not Drive-specific calls scattered everywhere — so swapping to Cloudflare R2 later (if content length grows, e.g. full Fredcasts episodes) is a contained backend change, invisible to how reporters use the app.

## AI pipeline (built by us, calling two backend APIs)

This is not "connecting reporters to Otter/CapCut/etc." — it's one app with two invisible infrastructure dependencies, same as any app depending on AWS or Stripe:

1. **Transcription** — AssemblyAI (~$0.20-0.25/hour of footage including speaker diarization). Auto-runs on upload; produces a timestamped, searchable transcript.
2. **Quote & clip flagging** — Claude API. Our own prompt/pipeline (not a third-party product) that reads the transcript and flags quotable moments with timestamps + reasoning.
3. **Social post generation** — Claude API. Takes flagged quotes + transcript context, generates 3-5 platform-variant drafts (copy only for v1; no auto-attached graphics yet).

Estimated AI cost: **under $0.50 per hour of raw footage processed** — at realistic testing volume (a handful of short clips/week across 3 people), total AI spend should be a few dollars a month, not a budgeting concern for v1.

## Data model (working draft)

```
Project
├── id, name, created_at, owner (Nick or a tester), tags
└── Assets[]
    ├── id, type (video | audio)
    ├── source_file (Drive file reference)
    ├── duration, uploaded_at
    ├── transcript (text + timestamps)
    ├── flagged_quotes[] (timestamp, text, reason)
    ├── generated_social_posts[] (platform, copy, based_on_quote_id)
    └── status (uploading | transcribing | ready | error)
```

## Stack (proposed, open to revisit once we start building)

- **Frontend/backend:** Next.js (React + API routes in one framework — simplest for a solo/small-team web app)
- **Database:** Postgres (via a managed host — e.g. Supabase or Neon — avoids running our own DB server)
- **Auth:** Simple email/password or Google sign-in (matches the Drive OAuth we need anyway)
- **File storage:** Google Drive API, behind an internal storage abstraction
- **Transcription:** AssemblyAI
- **AI extraction/generation:** Claude API (Sonnet 5)
- **Hosting:** Vercel (frontend/backend) — free tier likely sufficient for this testing phase
